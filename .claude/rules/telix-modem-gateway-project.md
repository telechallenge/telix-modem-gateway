# Project: Telix Modem Gateway

**Last Updated:** 2026-08-06

## Overview

Virtual Hayes-compatible modem gateway. Telnet clients connect, issue AT commands, and dial phone numbers to reach backend BBS systems via TCP. Includes a web terminal client (Node.js/WebSocket → xterm.js).

## Technology Stack

- **Language:** Go 1.24 (gateway), Node.js (web client)
- **Dependencies:** `golang.org/x/time` (rate limiting), `lumberjack.v2` (log rotation), `yaml.v3` (config)
- **Web client:** Express, `ws` (WebSocket), xterm.js (browser terminal)
- **Container:** Docker multi-stage build, Docker Compose (gateway + web client; fail2ban is present but behind an off-by-default profile)
- **CI:** SLSA Go releaser (`.github/workflows/go-ossf-slsa3-publish.yml`)

## Key Architecture

- **Session lifecycle:** `server.go` accepts TCP → creates `Session` → `session.go` runs command/data loop → `modem` package handles AT parsing + state
- **Modem state:** `StateCommand` (reads AT commands) ↔ `StateData` (bridges client ↔ remote BBS)
- **Phonebook matching:** Numbers normalized (strip `-().# ` etc.), entries can require `init`, `baud`, `error_correction`, `compression` — mismatched settings produce garbage + NO CARRIER
- **Always-busy entries:** `busy: true` on a phonebook entry makes the number permanently engaged — `handleDial` reports BUSY and returns before any dial is placed. Checked *before* `checkRequiredSettings` and before the password gate, because a busy line is engaged ahead of ringback, negotiation and login; `sendBusy` therefore sends no RING. Config validation skips the host/port requirement for these entries, so a number that never dials doesn't need an invented unreachable host
- **BUSY never follows RING.** The invariant covers both routes to a busy signal — a `busy: true` entry and a refused TCP connection — because ringback is the caller's evidence the line was *free*, and ringing before BUSY is a sequence a real line cannot produce. What buys the guarantee is `callSetupPause` (1.2–2.0s, the gap a real call spends being routed): the dial goes out in its goroutine, `handleDial` spends the gap, then takes a *non-blocking* read of the result channel before the first RING. A refusal is a one-RTT RST, so it is essentially always back inside that window. The rare refusal that misses it reports **NO CARRIER**, not BUSY, since the caller has already heard ringing — which also means `isConnectionRefused` is consulted at exactly one place. Restructuring this is what removed the duplicated success/failure blocks that used to live inside the extra-ring loop; the trap to avoid re-introducing is the reverse one, a dial that resolves *successfully* during the setup gap must still ring before CONNECT (regression-tested in both directions)
- **Password-gated entries:** an entry with `password` takes the `gatedConnect` path in `dial.go` — RING, then CONNECT, *then* the `PASSWORD:` prompt, so it reads as the BBS's own login rather than a gateway-side gate. The outbound dial is only placed after the password is accepted (a wrong guess never reaches the host), and success enters data mode without a second CONNECT since the terminal already saw one
- **Telnet filtering:** `TelnetFilter` (IAC state machine in `internal/dialer`) filters telnet commands from data streams in both directions. Go server handles all negotiation; web client is a passthrough proxy (CP437→Unicode only)
  - The BBS-facing filter is built with `NewRemoteTelnetFilter()`, which additionally infers whether the peer speaks telnet: a peer that answers negotiation has its doubled `0xFF` un-escaped as usual, while a raw TCP peer's `0xFF` passes through untouched. The verdict is locked once a ZMODEM frame header appears, so file data can never flip it. Client-facing input uses plain `NewTelnetFilter()` — the web proxy always doubles `0xFF`, so that contract is unambiguous
  - **ZMODEM detection:** `zmodem-sentry.js` slices inbound data so each ZMODEM hex header ends a chunk. zmodem.js only fires a detection when its input *ends* with a header, and a coalesced ZRQINIT pair otherwise wedges detection permanently
  - **Partial headers:** a header straddling a TCP chunk boundary is held back in `headerTail` and prepended to the next chunk, in both the detecting and the live-session path. A header only counts as complete once its `CR LF` terminator has arrived — zmodem.js cannot parse one without it. `scheduleTailFlush` releases a fragment after 100ms so nothing is ever swallowed. This is what made batch downloads fail while single-file worked: the longer preamble moved the chunk boundary into the header
  - **ZRQINIT retransmits vs. per-file sessions:** a ZRQINIT arriving during a live receive session is ambiguous. Before the session's file offer arrives it's a retransmit (sender hasn't seen our ZRINIT) — zmodem.js throws `Unhandled header` on it, wedging the download — so `feed()` drops it (`isZrqinitHeader` + `sessionSawOffer === false`). After the offer, the file is already delivering, so a ZRQINIT is the *next* file's session: some BBSes (DOS DSZ/GSZ behind a telnet bridge) drive a multi-file download as one session per file and **never send ZFIN between them**, so the old session never closes itself. `resetSession()` drops the stale session and rebuilds the Sentry (its internal `_zsession` would otherwise still point at the dead session and throw). Without this only the first file arrived. Regression-tested with real zmodem.js on both ends (`per-file sessions without ZFIN`)
  - **Uploads (client→BBS):** `dataLoop` mirrors the read side — `appendRemote` re-doubles `0xFF` when `filter.PeerSpeaksTelnet()`, since the client-side filter has already collapsed the proxy's doubled bytes. The whole read chunk is written in one `Write`; per-byte writes cost ~7× throughput. Escape characters withheld pending a `+++` decision are flushed to the BBS when the guard time proves they were not an escape
  - **ZMODEM uploads:** the send session is only confirmed once the user has picked files (`beginUpload`), because `rz` repeats ZRINIT every ~10s and zmodem.js throws if a live session sees a second header. `files_remaining` must be omitted rather than sent as `0`
  - **Non-zero ZRINIT buffer (DSZ/GSZ, Searchlight):** zmodem.js only supports streaming receivers (buffer size 0) and throws `Buffer size unsupported` on any other ZRINIT — the Sentry swallows the throw, so uploads to a DOS BBS never even open the picker. `adaptZrinitForSender` in `zmodem-sentry.js` rewrites an inbound ZRINIT to advertise buffer 0 (preserving the capability flags, recomputing the CRC) before it reaches the Sentry. Vendored library stays untouched
  - **Honouring the advertised window (`applyWindowedSend`):** the rewrite above is a lie and only half a fix — the receiver asked for windowing and we told it that it didn't. zmodem.js's sender is firehose-only by design ("Sender opens the firehose … all ZCRCG (!end/!ack) until the end"), so nothing else paces the send and the entire file goes out in one burst. Searchlight BBS 5.1 advertises `buffer=8192`, cancels the overrun with `CAN`×8 and drops carrier; **the browser still shows 100%**, because progress counts bytes handed to zmodem.js, not bytes acknowledged. `applyWindowedSend` overrides `_send_interim_file_piece` on the session to send at most `windowSize` bytes, close the frame with `ZCRCW` (`end_ack`), and wait for the `ZACK` — resetting `_sent_ZDATA` so the next frame re-announces its offset. `readZrinitWindow` must run *before* `adaptZrinitForSender`, which zeroes the field it reads; only a non-zero reading updates it, since the ZRINIT answering our ZSINIT may report 0 and dropping back to firehose mid-file is the bug itself. Two traps: `send_offer` binds the send method when it builds the Transfer, so the override must be installed first; and `Transfer.send()` **discards** its send function's return value, so the in-flight ZACK wait is parked on the session and awaited via `sendChunk`. Regression-tested against real zmodem.js (`a windowed receiver is paced…`, plus a streaming counter-case) and end-to-end against a real `rz` whose ZRINIT is rewritten to advertise a window
  - **A file smaller than the window (`_ackFinalPiece`):** pacing to the window is not enough on its own, because a file *shorter* than the advertised window never fills it — so no frame ever closes with `ZCRCW` and the whole upload goes out unacknowledged (every subpacket `ZCRCG`, the closing one `ZCRCE`, both "no ack" — zmodem.js: *"Sender opens the firehose … all ZCRCG until the end, when we send a ZCRCE"*). The sender then holds **no evidence at all** that a single byte landed: the only thing it waits for is the ZRINIT after ZEOF, and that is byte-identical to the ZRINIT a receiver re-announces when it has given up. A 4279-byte upload to Searchlight that arrived nowhere therefore printed `receiver acknowledged the file` / `session closed cleanly` with the browser at 100% — the same false success the windowing work was meant to end. `handleSend` now marks the file's last slice so it closes with `ZCRCW`, and refuses to report success unless a ZACK actually came back (`_ackCount`), with the ZACK's offset corroborating when the receiver reports a real one. A bare ZACK carries offset 0 — zmodem.js defaults `_bytes4` to four zero bytes and `ZACK_HEADER extends Header`, not `ZOffsetHeader`, so there is no `get_offset()` and the *count* is the load-bearing signal. Regression-tested both ways (a stale ZRINIT must not read as success; a ZACK must complete), and live against `rz` at 4279 bytes
  - **A refused offer is not a delivered file (ZSKIP):** `send_offer` resolves `undefined` for exactly one reason — the receiver answered the ZFILE with `ZSKIP` — and `handleSend` reported that as `endXfer({status:'done'})`, i.e. a successful upload, when the BBS had refused the file before a single data byte was sent. Searchlight prints `Checking for duplicate filenames...` before the offer and skips a name it already holds, so this is exactly what a *repeat* upload of the same file looks like — and the `NO CARRIER` that follows is its own `Disconnect after Upload?` setting, not a fault. The skip now traces the refusal, surfaces an error bubble, and ends the strip as `⊘ REFUSED` via a distinct `skipped` status. Reading a ZSKIP as success is what made a duplicate-name refusal indistinguishable from the windowing bug above
  - **Data subpacket size is chosen per receiver (`chooseBlockSize`):** ZMODEM specifies 1 KiB data subpackets; zmodem.js allows 8192 because lrzsz does (`MAX_CHUNK_LENGTH = 8192, //1 KiB officially, but lrzsz allows 8192`), and we once sliced at 4 KB — four times the legal maximum. lrzsz accepts that, so every test against `rz` passed. **Searchlight BBS 5.1 does not:** it answers the ZEOF with `ZRPOS 0` ("start over") and loops there until the transfer is cancelled, so the file never lands and the browser still reports 100%. Content-independent — ANSI, ZIP and plain ASCII all failed identically. Confirmed against the live BBS: 4 KB slices fail every time, 1 KiB slices give `Received file ... successfully.` **But 1 KiB for everyone is not right either:** ENiGMA½'s two default upload protocols are `sexyz -telnet -8 rz` and lrzsz `rz`, named "ZModem 8k (SEXYZ)" and "ZModem 8k", and both assemble subpackets into an 8192-byte buffer. Nothing in the protocol negotiates the sender's subpacket size — that is exactly why "ZMODEM-8k" is a menu entry rather than a ZRINIT flag — so the choice is inferred from the one thing the receiver does state, its receive buffer: **windowed (buffer > 0) → 1024, streaming (buffer 0) → 8192.** The two populations line up with that split (Searchlight advertises a window; lrzsz/sexyz advertise 0 and stream to disk), and the inference is empirical, not guaranteed, so `ZMODEM_BLOCK_SIZE` pins either size for a board that disagrees. Regression-tested in both directions by measuring the longest run of an unescapable payload byte on the wire, and live against real `rz` (byte-identical at 8 KiB; ~15% faster than 1 KiB over 8 MiB)
  - **A send needs a header handler that stays installed (`armSendHandler`).** zmodem.js's streaming sender registers **none** for the data phase, and `_consume_header` reads `_next_header_handler[NAME]` straight off a null — so any header the receiver sends kills the upload (`Cannot read properties of null (reading 'ZRPOS')`). It also nulls the field on **every** dispatch and reinstalls on a microtask, so installing one once is not enough: lrzsz repeats its ZRPOS and the second one walks into the same null. The handler therefore re-arms itself and covers the whole send. Two moments matter and **both** must be handled or the upload dies — mid-stream, and during the wait for the ZEOF acknowledgement, because a streaming sender empties the entire file onto the wire long before a complaint can travel back (measured against real `rz` with one byte corrupted 100 KB into a 512 KB file: the ZRPOS arrived only after the last byte had gone out). `endFile` wires *both* its own ZRINIT branch and the library's promise, since a windowed send owns its handler and `armSendHandler` deliberately leaves that alone — wiring only ours hangs every windowed transfer
  - **Every inbound header is named on the terminal (`<- ZRPOS offset=0`).** Only ZRINIT used to reach it, and that left the decisive question about a failing board unanswerable from a pasted session: a `ZRPOS 0` answering our ZFILE is the offer being *accepted*, while the same header at any other moment means the receiver lost sync — identical bytes, opposite meanings, told apart only by where they fall. Capped at 24 per session so a peer stuck retransmitting cannot bury the text it is meant to explain. The healthy shape against real `rz`, worth recognising: `<- ZACK offset=1` (our ZSINIT), `<- ZRPOS offset=0` (offer accepted), data, ZRINIT, `<- ZFIN`
  - **ZMODEM cannot escape `0xFF`, so IAC doubling is a transport decision and the phonebook owns it (`telnet:`).** ZDLE escaping is `c ^ 0x40` and the receiver only accepts an escape where `(c & 0x60) == 0x40`, i.e. **only `0x00-0x1F` and `0x80-0x9F` are escapable** — which is exactly why zmodem.js's table marks everything with bit 5 or 6 set "never escape" (`i & 0x60`). So the raw ranges on the wire are `0x20-0x7F` **and `0xA0-0xFF`**, and nothing in-band can protect `0xFF`. The gateway infers doubling from whether the board answered negotiation, which is right for anything modern and can be wrong **in either direction** for a 1990s DOS board behind a telnet front end. Too few doublings (front end eats IAC but never negotiates → inference says "raw") and it swallows each `0xFF` with the byte behind it; too many (front end negotiates but its app reads the socket raw → inference says "telnet") and the extra `0xFF` lands *inside the file*, breaking every subpacket CRC. **Both look identical from outside** — and identical to each other — because ASCII contains no `0xFF` to mangle, so the direction cannot be guessed from the symptom and `{"event":"outbound_iac"}` is the only way to tell. Symptom is exact and worth recognising: every binary upload rejected at `ZRPOS 0` forever, every plain-ASCII one fine. Measured live — ENiGMA½ uploads working while MajorBBS failed on the same gateway, same browser, same file. `telnet: auto|yes|no` per entry overrules it; a typo is a startup error, not a silent fall back. `{"event":"outbound_iac",...}` logs the verdict once per session at the first `0xFF`, because it is otherwise invisible from both ends. A browser-side toggle was tried for this and removed: one `localStorage` key for every board, when the fault is per-board and the gateway already decides it per entry
  - **There is no transfer-tuning UI, and that is the conclusion, not an omission.** A per-upload block-size picker and an IAC toggle were both built and both removed. Block size cannot be detected — but with auto at 1 KiB and the ZRPOS fallback below it, nothing is left to choose. The IAC toggle was worse than useless: one `localStorage` key for every board when the fault is per-board, duplicating a decision the gateway already makes per phonebook entry, and turning it on against ENiGMA½ made uploads fail immediately. A browser-side doubling layer was built on a `sexyz -telnet` theory that no board ever confirmed; the gateway's `telnet:` setting is the only place that knows which board a call reached, so it is the only place that decides
  - **A board refusing a file on size answers `ZRPOS 0` forever, and that is indistinguishable from a corrupt link.** MajorBBS states `Maximum upload size: 200000 bytes` on its upload menu; a 121,779,977-byte file was offered anyway, the ZFILE was answered with `ZRPOS 0` (which reads as *accepted*), and every data subpacket was then refused at every block size and every telnet setting. Hours went into escaping theories for what was a stated limit printed on the screen above the transfer. **Check the board's per-file limit first** — the give-up message now quotes the file size for exactly that comparison, and names the size hypothesis ahead of the escaping one
  - **Auto block size is 1 KiB, and the "streaming ⇒ 8k" inference is dead.** It held for lrzsz and sexyz and was falsified by MajorBBS, which advertises buffer 0, refuses 8 KiB with `ZRPOS 0`, and accepts the identical file the moment the fallback drops to 1 KiB (watched live on a 6206-byte text file that succeeded on the retry). The trade is lopsided: guessing 8 KiB on a board that refuses it costs a full re-send of everything already in flight — megabytes on a large file — while guessing 1 KiB where 8 KiB would have worked costs ~15% throughput measured against real `rz`. 8k is opt-in via the prompt or `ZMODEM_BLOCK_SIZE`
  - **A receiver stuck at ZRPOS 0 is not a block-size problem, and the retry budget says so.** If the receiver has never rewound past 0 it has never accepted a data byte — while the ZFILE offer *did* get through, and a ZFILE payload is plain ASCII. Binary headers work (ZDATA and ZFILE are both `to_binary16`) and ASCII subpackets work; only binary subpackets fail. That is byte-content dependence, and the suspect is 0xFF: telnet IAC is the one byte the whole path treats specially. Measured against ENiGMA½, `sexyz -telnet -8 rz` fails this way from the first subpacket while lrzsz `rz` (same board, same gateway, no `-telnet`) delivers a whole file intact — so the double handling is on the sexyz side of the gateway, not ours (`TestDataLoop_DoublesIACForTelnetPeer` pins our half). One retry is therefore the budget when `accepted == 0` (spent on the block-size fallback, which is the only cheap hypothesis), versus `MAX_REWINDS` when the receiver is actually making progress — on a 116 MB upload each wasted round is a full re-send
  - **ZRPOS is honoured, not fatal.** It is ZMODEM's repair signal and the file is already in memory, so the sender rewinds to the offset (`_sending_file = true`, `_file_offset = target`, `_sent_ZDATA = false` — `end()` clears the first two) and drops to 1 KiB for the rest, capped at 3 rewinds. Verified end-to-end: corrupting one byte in flight makes real `rz` issue a ZRPOS, and the file still lands byte-identical with `rz` exiting 0
  - **Nothing on the wire distinguishes a board that takes 8k from one that does not**, so `chooseBlockSize` sends 1 KiB and the ZRPOS fallback corrects any board that disagrees. A per-upload picker was built for this and removed — see "no transfer-tuning UI" above. Note the fallback is expensive on a big file: a streaming sender has already put everything on the wire before the ZRPOS returns
  - **A keep-alive ZRINIT must be dropped when the send session has no handler for it:** `_consume_header` reads `this._next_header_handler[hdr.NAME]` and sets that field to **null** the instant it dispatches, reinstalling the next handler on a *microtask*. `splitAtHeaderBoundaries` feeds every header of a chunk in one synchronous turn, so two headers in one TCP segment land either side of that null and the second throws `Cannot read properties of null (reading 'ZRINIT')`. **SEXYZ hits this every time:** it answers our ZSINIT with ZACK and then loops straight back to re-announcing itself, so ZACK+ZRINIT arrive together and the upload dies before the ZFILE — while zmodem.js's promise chain carries on and sends the ZFILE anyway, which is why the receiver's `ZRPOS 0` then prints as line noise on a session the bridge has already torn down. That stray ZRPOS in a bug report is the signature. A send session only *wants* a ZRINIT where it registered one (after ZEOF, and `_end_file` registers it before sending the ZEOF), so `!handler || !handler.ZRINIT` → drop. Verified end-to-end that the post-ZEOF ZRINIT still gets through
  - **The ZEOF acknowledgement gets its own, size-derived timeout.** The receiver cannot answer until it has absorbed everything still buffered between browser and BBS, and `bufferedAmount` draining says nothing about that — nginx, Cloudflare and the gateway each hold a queue, so the browser can finish long before the far end has. The wait is `clamp(data-phase seconds, zmodemTimeoutSec, 600)`: how long the file took to push is the best available measure of how long the far end can still be busy with it. Also: **the timeout path now traces.** It used to abort in silence, which is why every failing session anyone pasted stopped mid-sentence, indistinguishable from the BBS hanging up
  - **The send loop must wait for the socket (`drainWS`):** `ws.send()` appends to a buffer and returns, and nothing above it blocked either, so `handleSend` used to hand zmodem.js an entire file as fast as JavaScript could escape it. Three things followed, all of them wrong: the browser painted 100% before the transfer had really started, memory held the whole file twice over, and — the failure that actually killed uploads — **the idle timer stopped being re-armed once the loop finished**, so the session was aborted `zmodemTimeoutSec` later while the first megabyte was still on the wire. Silently, because the timeout path does not `trace()`. That is how a 116 MB upload to ENiGMA½ ended at `all 121779977 bytes sent, waiting for the receiver` with nothing after it. The loop now drains to a low-water mark before queueing more, and re-arms the timer **only when `bufferedAmount` has actually fallen**, so a genuinely stalled link still times out instead of being held open by its own backlog. `web/server.js` needs the matching half (`ws.pause()` when `tcp.write()` returns false, resume on `drain`) — without it the backlog merely relocates into the proxy's heap, the browser watches its own socket empty and believes the file has landed. Note a trap when writing tests for this path: a binary frame whose **first byte is `0x00` is read as a NAWS resize message** and replaced by 9 bytes of subnegotiation, so a payload ramp starting at zero silently never reaches the gateway
  - **Surviving an unexpected header:** zmodem.js throws on any header its current `_next_header_handler` does not list, and the throw escapes `bridge.consume()` into the WebSocket message handler where nothing catches it — the bridge stops pumping and the terminal dies with nothing on screen, indistinguishable from the BBS hanging up. `feed()` catches it, reports via `trace()`, ends the transfer and rebuilds the Sentry. Reachable in practice: Searchlight answers a rejected ZEOF with `ZRPOS` while we wait on `ZRINIT`
  - **Diagnosing a windowed receiver:** the ZRINIT echoed to the terminal is the *post*-rewrite header, so a BBS asking for 8192 and one asking for nothing both display as `0100000023be50`. `feed()` therefore logs the pre-rewrite header to both the console and the terminal (`[zmodem] ZRINIT buffer=… raw=<…>`); the terminal copy is the one that survives being pasted into a bug report
  - **Upload picker needs a user gesture:** a file `<input>` only opens its dialog during transient user activation, which a WebSocket frame (the BBS's ZRINIT) doesn't have — so `promptUpload` surfaces a "Choose files" button and opens the picker from *its* click, mirroring the download Save button. Calling `input.click()` straight from the network event is silently blocked and no dialog appears
- **nginx vhosts (`nginx/nginx.conf`):** one TLS listener on 443 routes by `Host` — `pcpursuit.net`/`www.pcpursuit.net` → `telix-web:3000`, `mon.pcpursuit.net` → `grafana:3000`. Everything crosses Cloudflare and a `geo` check on `$realip_remote_addr` rejects any peer outside the CF edge ranges. Five things a future edit must not undo:
  - **The `default_server` block returning `444` is load-bearing.** Name-based routing sends an unmatched `Host` to whichever block loaded first, so without it a request for any hostname — or a direct hit on the origin IP — quietly gets served one of the apps under the wrong name
  - **`proxy_set_header` lives at `http` level and its inheritance is all-or-nothing.** nginx inherits the set "if and only if there are no `proxy_set_header` directives defined on the current level", so adding one header inside a location silently discards *every* other — `Upgrade`/`Connection` go first, killing the terminal's WebSocket, and `Host` reverts to `$proxy_host`, which makes Grafana build redirects from the upstream name. Verified working by a real `101 Switching Protocols` through the production Cloudflare path
  - **Grafana's `Cf-Access-Jwt-Assertion` check is a failsafe, not authentication.** Cloudflare Access is the real gate; the header check only asserts Access is still in front. Worthless against a forged header, but it fails *closed* if the Access app is deleted rather than exposing the monitoring stack with only Grafana's login in the way. The cost is that `mon.*` returns 403 until an Access application exists
  - **`GF_SERVER_ROOT_URL` must track the `mon.*` `server_name`.** Grafana builds absolute URLs from `root_url`, not from `Host`, and nginx does not expand env vars — so the hostname is deliberately written in two places with cross-referencing comments rather than one
  - **Recreate nginx after a config edit; never `-s reload`.** The config is a single-file bind mount and an edit that writes a new file leaves the container on the old inode, so a reload re-reads the **old** config — measured here, the container reported 0 matches for the new vhosts while the host file had them. `docker compose up -d --force-recreate nginx`. Identical to the `prometheus.yml` trap below. `depends_on: grafana` exists because nginx exits at boot if an upstream name does not resolve
- **Web client security headers + SRI (`web/server.js`, `index.html`):** one `securityHeaders` middleware in front of every route — CSP, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, COOP/CORP — plus `app.disable('x-powered-by')`. Hand-rolled rather than helmet for the same reason `web/metrics.js` is hand-rolled: `npm ci` aborts when `package.json` and the lock disagree, so a new dependency means regenerating the lock, and none of helmet's per-request machinery is in play for a fixed header set. Four things a future edit must not undo:
  - **`style-src 'unsafe-inline'` is required and `script-src 'unsafe-inline'` must never be.** xterm builds a `<style>` element at runtime for cell metrics and theme and accepts no nonce, so inline style cannot be covered any other way. There is no inline script in the app; keep it that way rather than loosening script-src
  - **`connect-src 'self'` covers the WebSocket.** `ws://`/`wss://` of the page's own origin match `'self'` under CSP3 — verified in a live browser session, TR lamp lit. Do not widen to bare `ws:`, which would allow dialling any host
  - **HSTS only when the request arrived over TLS** (`x-forwarded-proto`, which `nginx/nginx.conf` sets, else `socket.encrypted`). Sending it unconditionally would promise TLS for a plain-HTTP deployment
  - **The CDN URLs are the files npm publishes (`lib/xterm.js`, `css/xterm.css`), not jsdelivr's `.min.` variants.** The `.min.` files exist nowhere in the registry — jsdelivr minifies on demand — so their bytes cannot be verified against anything, and a change to jsdelivr's minifier would break the pinned hash and blank the terminal. The hashes in `index.html` were confirmed byte-identical to the npm tarballs, whose sha512 matches the registry's published integrity. Costs ~2.4 KB, since the published `lib/xterm.js` is already a production bundle. `integrity` without `crossorigin="anonymous"` blocks the load outright — the browser cannot read the body to hash it. Enforcement is regression-tested by flipping one character of a hash and confirming the browser refuses the script (`Failed to find a valid digest`); `stampAssetUrls` leaves these URLs alone because they carry a scheme

- **The `+++` escape detector must not fire on a streaming client (`lastBulk` in `dataLoop`).** This was the intermittent large-upload failure, and it is worth understanding in full because the symptom names nothing:
  - Binary file data contains `+++` every few tens of megabytes. The Hayes rule accepts an escape after guard-time silence — and the browser's **own backpressure** (`drainWS`) pauses the send loop while its socket drains, manufacturing exactly that silence on both sides of those bytes. So the gateway quietly left data mode mid-transfer. The BBS then simply stops receiving: `rz` times out and **deletes the partial file**, prints no protocol error, and *neither socket closes*. Nothing anywhere says "escape". It presents as an intermittent network fault, and it is size-dependent only because a bigger file rolls the dice more often
  - Two separate defects had to go. First, `preEscapePause` was a flag set by whatever *non-escape* byte last arrived, so a chunk like `Q+++` inherited the pause that preceded the `Q` — the guard time must be silence immediately before the `+` itself. Second, and unfixable by guard time alone, a chunk that *begins* `+++` after a drain pause is byte-for-byte a typed escape. **Volume is the only discriminator**: a caller cannot type 64 bytes in one read (`readBuf` is 256), a ZMODEM sender does nothing else, so escapes are ignored for 5s after any full-ish read
  - The gate must wrap the **whole** `if b == escapeChar` branch. Testing it inside, on the `escapeCount == 0` arm, sends a streaming `+` to the "subsequent escape char" arm which counts it anyway — reintroducing the bug while every unit test still passes
  - Diagnosing this needed per-hop byte counters (`web/e2e/upload-stress.js`): `bridge-sent=49.7MB` against `bbs-in=29.4MB` with only 256 KB in the WebSocket buffer is what localised it to the gateway having stopped reading. Direct-to-`rz` tests all passed because they bypass the gateway entirely — the hop the bug was in
- **Config hot-reload (`internal/config/watch.go`, `Server.Reload`, `reload:` in the config):** the file is polled and an edit is applied to the running gateway, so adding a board does not mean restarting and dropping every call in progress. Seven things are load-bearing:
  - **The config's *directory* is bind-mounted, not the file, and the feature does not work without it.** A single-file bind mount pins the host inode; vim and `sed -i` save by writing a new file and renaming it over the old, so the container keeps reading the original inode and never sees the edit. Measured both ways: through a file mount an in-place `>>` append is visible while a write+rename is **stale forever**, and a container on the old mount still saw one phonebook entry after the host file had two, with zero reloads fired. It must also be a **sibling** of the banners mount rather than its parent — mounting `./configs` at `/etc/telix` makes that path read-only and Docker then cannot create the `/etc/telix/banners` mountpoint inside it, so the container **fails to start at all**. Hence `./configs:/etc/telix/conf:ro` plus a compose `command:` pointing at it; the image's baked `/etc/telix/telix.yaml` stays as the default for a bare `docker run`
  - **Detection is a content hash, not mtime.** Same reasoning as `banner_art.go`: Linux serves a coarse cached clock to filesystem timestamps, so a same-tick write can leave mtime byte-identical. A hash also treats "edited and reverted" as no change, which mtime cannot, and the file is a few KB so hashing costs less than the read that fetched it. The baseline comes from `Config.sourceHash()` — the digest of the bytes the *running* config was parsed from — rather than from re-reading the file at watcher start, which would leave a window where an edit landing between load and watch is adopted as the baseline and therefore never applied
  - **A config is applied only if it parses AND validates**, which is what makes polling safe against a save in progress: a truncated file fails one of those, and because the completed save hashes differently it is picked up on the very next poll rather than being remembered as already-seen. The last-considered hash is recorded for *rejects* too — otherwise a permanently broken file re-reports itself every poll — but recording it under its own digest is what stops that suppression from also swallowing the operator's fix
  - **The config is swapped as a whole pointer (`atomic.Pointer[config.Config]`), never mutated.** That is what keeps the session hot path lock-free and free of torn reads: `handleConnection` reads the pointer once and hands it to `NewSession`, so a caller mid-call keeps the phonebook they dialled under and an edit can never re-point a live session underneath itself. Regression-tested in both directions
  - **What cannot reload is *reported*, not silently dropped.** `server.port`, `metrics.*`, `logging.file` and `logging.format` configure something already bound, so `Reload` returns their names and the log line carries `needs_restart`. A setting that changed in the file but not in the process is the one outcome an operator would never otherwise discover — they see "reloaded" and assume all of it landed. `cfg.Version` must also be carried across, since it is set from the build stamp and never appears in YAML: taking the parsed config at face value blanks the banner, `ATI` and the Grafana Version panel
  - **The limiters are updated, not rebuilt** (`SetLimits` on both, mirroring `SetTrustedProxies`), because rebuilding would discard the in-flight attempt and block state — raising a limit should not thereby forgive whoever is currently blocked. The prober is the opposite case and *is* rebuilt, through the same constructor startup uses, so the phonebook, probe interval and `allowed_networks` all take effect by one path rather than a second one that could drift
  - **Metrics series must be reset before republishing (`ResetPhonebookSeries`).** These are GaugeVecs keyed on entry and address, so a board deleted from the phonebook would keep publishing its last value — a removed line reading as configured forever, and worse, `telix_bbs_reachable 1` asserting a board is up that the gateway can no longer dial. That is the same failure `telix_bbs_last_probe_timestamp_seconds` exists to catch, arriving by another route. Cost is a brief "No data" on the reachability panels until the next cycle, which is seconds away because a rebuilt prober probes immediately — and consistent with those series deliberately not being pre-created

- **Reachability probing (`internal/probe`, `probe:` in the config):** the gateway dials every non-busy phonebook entry's `host:port` on a timer and publishes `telix_bbs_reachable{entry,address}`, drawn as the dashboard's **BBS reachability** row. It exists because nothing else in the stack can answer the question: a board in a container reports healthy whether or not its listener works, and a board on somebody else's host is invisible until a caller gets NO CARRIER. Seven things are load-bearing:
  - **The probe does not negotiate telnet** (`dialer.Probe`, deliberately not `Dial`). A BBS treats terminal-type chatter as the start of a call and writes it to its caller log, so a negotiating probe would post a phantom call there every interval. The unit test asserts *zero bytes* reach the listener, which is the only way that stays true
  - **`allowed_networks` binds it exactly as it binds a dial.** The one thing that contacts every phonebook host on a timer must not be the one thing exempt from the setting that exists to stop that
  - **Off when the section is absent**, matching the `metrics:` contract, and `interval` has a 10s floor (`config.MinProbeInterval`, clamped not obeyed). Enabling it makes the gateway connect to hosts other people own — `telehack.com` is in the shipped phonebook — so an upgrade must not start doing it unasked
  - **Busy entries are skipped.** They place no outbound call, so their host is on no path a caller can take, and `validate()` does not even require them to name one — a probe would dereference a field the config says is optional
  - **Entries are deduped by address, one knock per board per cycle**, but each entry keeps its own series: the dashboard names lines, not sockets, and a board commonly answers to a primary and a priority number
  - **The reachability series are deliberately not pre-created**, unlike the rejection and byte counters. Zero means "refused a connection", so seeding them would announce every board down for the second before the first cycle answers — a false alarm on every restart is worse than "No data" for a moment
  - **Skipping busy entries makes the dashboard undercount the phone list, and `telix_phonebook_entry` is the fix.** The reachability gauges only exist for lines the prober dials, so adding ten always-busy numbers changes nothing on the timeline — indistinguishable from a prober that died, and the reason "the dashboard is not reflecting changes to the phone list" was reported as a bug when every hop was in fact in sync. The inventory gauge is published at startup and again on every config reload (`publishPhonebook` in `cmd/telix/main.go`), one series per configured line labelled `entry`/`address`/`busy`, and drives the **Lines configured**, **Always busy (not probed)** and **Phone list** panels. Three things it is careful about: `address` is empty rather than `":0"` for a busy line that names no host, since `JoinHostPort` would render an endpoint that does not exist; an unnamed line is labelled `unnamed`, never its dialled number, for the same cardinality reason `telix_dials_total` uses the phonebook name; and because it tracks the live phonebook, the table doubles as the check for whether a config edit actually reached the gateway — an added entry still missing here means the file being read is not the one edited (check the bind mount), not that the probe is broken. Probing the busy entries instead was considered and rejected — 7 of the 9 here point at `host.docker.internal:22023`, which is Terminal Velocity's address, so they would have drawn seven duplicate lines of one board's status
  - **A reachability gauge alone is a trap**, which is why `telix_bbs_last_probe_timestamp_seconds` exists and gets its own panel: if the loop dies the last verdict sits there reading UP forever, and nothing about the value itself would ever say otherwise. Transitions are logged (`probe_reachable` / `probe_unreachable`), *only* transitions — one line per board per cycle is 28,800 lines a day on a 20-entry phonebook
- **Monitoring stack:** Prometheus + node_exporter + Grafana in `docker-compose.yml`, scraping over `telix-net` by compose service name, so no target publishes a port to the host.     - **`bips` is not "currently banned".** fail2ban purges lapsed rows lazily, so an unfiltered read reports IPs that are free to connect — a real stale row was sitting there while `fail2ban-client` said 0 banned.   - **The container build is version-stamped, and that is a diagnostic tool, not decoration.** The Dockerfile used to omit the `-X main.version` ldflag the Makefile passes, so every container reported `1.0.0` in the banner, `ATI`, the startup log and the dashboard's Version panel — leaving no way to tell a freshly deployed gateway from a stale one. That cost real time chasing a BBS-specific transfer fault: several rounds of "still failing" were run against code that had never been deployed, and the giveaway was that the *browser's* error text was a build behind. `ARG VERSION` in the Dockerfile, `TELIX_VERSION` in compose, and `make docker-up` now passes `git describe` and rebuilds. `VERSION` strips a leading `v` because the banner adds its own
  - **"Dials by phonebook entry" counts, it does not rate.** `rate()` is a per-second average that the panel then scales up, and on a gateway taking a handful of calls a day that scaling is the whole reading: one dial inside a ~35s `$__rate_interval` window is `1/30` dials/sec, which `* 3600` renders as **120 dials per hour**, and two dials landing in the same window as 240. The counter was right the whole time — the axis was showing an extrapolated hourly rate under a title that promises a count, so a handful of real dials read as 60–240. The panel is now a `bargauge` over `sum by (entry) (round(increase(telix_dials_total[$__range])))`: a plain count of dials inside the dashboard's time range. `round()` is not cosmetic — `increase()` extrapolates to the window edges and returns 2.02 for two dials. Two limits worth knowing: `increase()` cannot see across a gateway restart that leaves a series at the value it already held, so a restart can swallow at most one dial per entry; and `$__range` follows the time picker, so widening the range is what changes these numbers. The sibling **Dial outcomes** and **Rejected connections** panels are still `rate() * 60` — deliberately, since they answer "what is happening now" rather than "how many" — but they inherit the same extrapolation and should not be read as counts
- **BBS + VM monitoring** — three exporters beyond the gateway's own, each with a reason it is shaped the way it is:
  - **`monitoring/bbs-exporter` (ENiGMA½ boards):** reads each instance's SQLite databases read-only off a bind mount of `~/bbs/bbs_infra/instances`. The boards sit on isolated Docker networks (`bbs1net`/`bbs2net`/`bbs3net`) and expose no metrics endpoint, so the shared data directory is the only seam. Instances are **discovered** — any subdirectory holding a `db/` — so a fourth board needs no config change. Two traps, both measured on the live boards:
    - **`immutable=1` silently returns stale data on a WAL database.** It reads the main file and ignores the `-wal` alongside it: on bbs1 that read 12 users where `mode=ro` read the true 15. Only `mode=ro` is used and there is deliberately **no** immutable fallback — reporting the board down beats reporting a confident wrong number. `mode=ro` reads fresh even through a `:ro` bind mount; that was verified in a container, not assumed
    - **`system_event_log` and `user_event_log` are not append-only.** ENiGMA trims both with `DELETE` (`core/stat_log.js`: `appendSystemLogEntry` honours a keep count or age, `appendUserLogEntry` a `keepDays`) — read from the running container, not from memory. Anything counting rows in them is therefore a `*_recorded` **gauge**; published as a counter, every trim would read as a counter reset and `rate()` would invent activity. Same trap as the fail2ban `bans` table. Only the `system_stat` values (`login_count`, `ul_total_*`) are true counters, because `incrementSystemStat` is a read-add-write on a persistent property
    - Per-area series are capped at 64 with the shortfall in `enigma_areas_truncated`; timestamps are **omitted** rather than zeroed on a board nobody has called, since zero plots as 1970 and swamps the axis. bbs2/bbs3 are live proof — they are installed but empty, and every aggregate returns NULL
  - **`monitoring/docker-exporter` (per-container CPU/memory/network):** **cAdvisor does not work on this host and is not a matter of tuning.** Docker 29 uses the containerd image store (`Storage Driver: overlayfs`), so `/var/lib/docker/image/` holds only `identity-cache.db` — there is no `<driver>/layerdb` tree — and cAdvisor's cgroup-to-container mapping fails for *every* container (`failed to identify the read-write layer ID`). It comes up **healthy** and reports exactly one series, the root cgroup, so nothing ever reaches a panel. Three things about the replacement:
    - **It never touches the Docker socket.** `docker-socket-proxy` holds it and allows only `GET /containers/*`; the two talk over an `internal: true` network with no route off the host. Mounting `docker.sock` into a consumer is equivalent to giving it root, and `:ro` does not change that — the socket is an API and the API can create privileged containers
    - **Memory limits come from `HostConfig.Memory`, not `memory_stats.limit`.** For an unlimited container Docker reports the *host's* total RAM in the stats field, and a "limit" line at 16 GiB flattens a 10 MiB working set off the axis. Unlimited containers get no limit series at all. Memory itself is a working set (`usage - inactive_file`), which is what an OOM kill tracks
    - `stats?one-shot=true` is required: without it Docker samples twice a second apart before answering, and a dozen containers outlast the scrape interval. It also means no `precpu`, which is fine — CPU is exported as the cumulative counter and Prometheus rates it. `RestartCount` is a **gauge**: it resets to zero when a container is recreated
  - **`monitoring/vbox-exporter` (VirtualBox VMs):** the one piece that cannot live in a container — VBoxManage talks to VBoxSVC over the session owner's XPCOM IPC socket (`/tmp/.vbox-$USER-ipc/ipcd`), and a container has neither the socket nor the matching library tree. It runs as a **systemd `--user` unit** (`make vbox-exporter-install`), which needs no sudo. Four things are load-bearing:
    - **`PrivateTmp=true` would break it** — the IPC socket lives in `/tmp`, and a private namespace hides it, giving `vbox_up 0` with a "could not connect" that looks exactly like VirtualBox not running. Equally, `PrivateDevices=`/`RestrictSUIDSGID=` make systemd manipulate the capability bounding set, which an unprivileged user manager may not do: the unit dies at startup with `218/CAPABILITIES` before the exporter runs at all. Both were hit for real
    - **Everything is host-observed and the `Guest/*` family is deliberately not exported** — it needs Guest Additions, reads empty on the DOS guest, and would be guest-reported. Point-in-time gauges come from VirtualBox's collector via the **`:avg`** aggregate (the raw metric returns several samples in undocumented order); CPU *counters* come from `/proc/<pid>/stat` so Prometheus rates a monotonic counter rather than a pre-averaged percentage
    - **VirtualBox's `kB` and `MB` are binary multiples** — confirmed against this host, not assumed: `RAM/Usage/Used` matched `ps` RSS, and `Disk/Usage/Used` matched the sum of the VM's VDI files / 1024². **`/proc/<pid>/io` is not read**: `ptrace_scope=1` denies it even to the uid owning the process, so per-VM disk IO would be permanently empty rather than merely unavailable
    - **The inventory is what makes a dead VM visible.** A process scan cannot tell "powered off" from "exporter broken", so `list vms` + `showvminfo` supplies registered-but-stopped VMs and they report `vbox_vm_running 0` rather than vanishing. The collector's config lives in VBoxSVC, which forgets it if every VM stops, so the exporter re-arms `metrics setup` when a running VM has no samples
  - **Prometheus reaches the host exporter as `host.docker.internal:9103`** via `extra_hosts` on the prometheus service; that resolves to docker0 (`172.17.0.1`), which the exporter binds instead of `0.0.0.0` — reachable from every container, not from the LAN. Verified from a container on the compose network. A **down** target there means the systemd unit is not running, not that the VMs are gone
  - **The dashboard JSON is generated.** Edit `monitoring/grafana/dashboards/generate.py` and run `make dashboards`; five of the seven dashboards are two templates pointed at different instances, and hand-maintaining them guarantees a panel gets fixed on one board and not the others. `telix.json` predates the generator and stays hand-written. Counts use `round(increase(m[$__range]))`, never `rate() * 3600` — the same lesson the Dials panel above records. `axisSoftMax` on the percentunit CPU panels exists because Grafana scales an all-zero series to 0–100 raw, which renders as "10000%" and makes an idle container look broken
  - **`prometheus.yml` is a single-file bind mount**, so an edit that writes a *new* file leaves the container on the old inode and `/-/reload` quietly re-reads the **old** config — the job list simply does not change. `make monitoring-reload` recreates the container, which is the only reliable way. Hit for real during this work
  - **Compose does not expand `~` in a volume source** — it creates a directory literally named `~` and mounts that, and `bbs-exporter` then comes up healthy reporting zero instances. `BBS_INSTANCES_DIR` uses `${HOME}`

- **Banner art (`internal/server/banner_art.go`):** with `server.banner_dir` set, each caller is greeted by a random `.ANS` from that directory (compose mounts `./banners` at `/etc/telix/banners:ro`) instead of `buildBanner`. Nothing is cached, deliberately: the obvious mtime-keyed cache is quietly broken, because Linux serves a coarse cached clock to filesystem timestamps and a file dropped in within the same tick as the last scan leaves the directory mtime **byte-identical** — verified, not theorised — so new art would never be drawn. One readdir plus one small file read per *connection* is nothing next to the TCP handshake and the 100ms telnet-negotiation sleep that connection already pays, and accepts are capped at 50/sec besides. Four more things are load-bearing:
  - **The cursor park (`artSuffix`) is not decoration.** Scene art fills the grid to the last cell, and `sendResult(OK)` writes `"\r\nOK\r\n"` straight after — two line feeds from the bottom row, so the terminal scrolls twice and the top two rows of the art are gone before the caller sees them. Trimming the art cannot fix it: these pieces pad their lower rows with `0xDB` blocks drawn in *black*, which read as empty screen but are real cells. So the art ends `ESC[999;1H ESC[2A`, parking two rows short of the bottom and letting the result code land there. `ESC[999;1H` clamps to the client's real height, so it holds on an 80x24 web terminal and an 80x25 telnet client alike. Caught only in a browser — the byte-level probe passed the whole time
  - **SAUCE is matched explicitly, never by truncating at the first `0x1A`.** The DOS EOF byte does precede the trailer, but `0x1A` is also a perfectly good CP437 glyph (a right arrow) that art uses, so cutting there would eat real artwork. The 128-byte record is identified by its `SAUCE00` magic, its optional `COMNT` block sized from the comment count at offset 104, and only then is a preceding `0x1A` dropped
  - **The piece is chosen once per session** and held in `s.banner`, so `ATCLS` redraws what the caller connected to rather than shuffling under them
  - Oversized files are **skipped, not truncated** — half a file is a screen of garbage, and the built-in banner is a better answer. Any failure to read falls back the same way, so a bad file costs one connection its art and nothing else
- **CP437 encoding:** Banner uses raw CP437 bytes; web client translates CP437 → Unicode for browser display
- **Version:** Injected at build time via `-ldflags -X main.version=...` from `git describe`. Used in banner, ATI response.
- **Web client:** Per-IP WebSocket connection limiting (default 5, `MAX_WS_PER_IP` env var)
  - **The client identity comes from `X-Real-IP`, never from `X-Forwarded-For[0]`.** nginx *sets* `X-Real-IP` from `$remote_addr` (post-`real_ip`, so the CF-Connecting-IP Cloudflare vouched for), overwriting any copy the caller sent — whereas `X-Forwarded-For` is `$proxy_add_x_forwarded_for`, which **appends** to the caller's own header. Reading the first XFF entry therefore read a value the caller chose, handing every forged value a fresh `MAX_WS_PER_IP` budget: the limit was bypassable with one header. Regression-tested by opening `MAX_WS_PER_IP + 1` sockets that share an `X-Real-IP` while each forges a different first XFF hop, and asserting the last is closed `1008`. The XFF fallback takes the **last** hop (the one appended by the nearest proxy), not the first. This leans on `telix-web` publishing no host port, so nginx is its only reachable peer; exposing it directly makes both headers caller-controlled again
  - This is the one place in the stack that *does* know the real browser address. It stops there — the last hop to the gateway is plain TCP with nowhere to carry it. See the address-collapse note under fail2ban above

## Important Notes

- `required_init` field is deprecated — auto-migrated to `required_settings.init` at config load
- Error correction (`&Q5`) and compression (`%C1`) default to `true` in both modem state and phonebook entries
- S12 (escape guard time) has a minimum of 20 (400ms) to prevent trivial escape attacks
- The web client's CP437→Unicode table must stay in sync with the Go banner's byte values
- `dialer.allowed_networks` restricts outbound dials to configured CIDRs — **use in production** to prevent the gateway from reaching arbitrary hosts
